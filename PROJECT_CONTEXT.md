# PROJECT_CONTEXT.md

## Суть проєкту

Мобільний offline-first PWA для працівників підприємств, які хочуть швидко фіксувати прихід і вихід зі зміни, бачити зароблені гроші, контролювати історію, аналітику та графік.

Додаток не має акаунтів, серверної частини або інтернет-синхронізації. Усі дані зберігаються локально на пристрої користувача. Будь-які майбутні функції мають зберігати цю модель, якщо користувач прямо не змінить вимогу.

## Поточний технічний контекст

Репозиторій є React/Vite PWA:

- `src/main.tsx` - точка входу React.
- `src/app/App` - очікуване місце основного застосунку.
- `src/app/styles/global.css` - глобальні стилі.
- `public/` і `dist/` містять PWA-активи та зібраний результат.
- Скрипти з `package.json`: `npm run dev`, `npm run build`, `npm test`, `npm run preview`.

Перед реалізацією нових можливостей потрібно перевіряти фактичну структуру `src`, бо вона може змінюватися між сесіями.

## Продуктові екрани

Основні екрани:

- Таймер
- Історія
- Аналітика
- Графік
- Налаштування
- Онбординг

Перший екран досвіду має бути корисним, а не маркетинговим. Для цього продукту пріоритет має мати щоденний робочий сценарій: швидко відмітити прихід/вихід і побачити гроші.

## Доменні правила змін

Планові зміни:

- Перша зміна: `06:30-14:30`
- Друга зміна: `14:30-22:30`

Правила:

- Тип зміни визначається автоматично за найближчим плановим часом.
- Один день = максимум одна зміна.
- У будь-який момент може бути тільки одна активна зміна.
- Зміна стає активною після дії `Прийшов`.
- Активна зміна завершується після дії `Пішов`.
- Активна зміна не завершується автоматично, навіть після планового часу або перезапуску застосунку.
- Зміну не можна завершити, доки її активний тікет явно не завершено з фактичною кількістю.
- Кнопки `Прийшов` і `Пішов` працюють через утримання, щоб зменшити випадкові натискання.

Якщо в майбутньому буде повернуто автозакриття зміни або додано нічні зміни, ручну зміну типу чи декілька підприємств, це треба оформити як явну зміну доменних правил.

## Гроші і аналітика

Основна метрика додатку - гроші.

Аналітика і головний екран мають допомагати користувачу швидко відповісти на питання:

- скільки вже зароблено;
- скільки очікується за період;
- які зміни відпрацьовано;
- чи є відхилення від графіка;
- де були запізнення або ранні виходи, якщо така логіка реалізована.

Фінансові формули мають бути ізольовані від UI настільки, щоб їх можна було тестувати окремо.

Поточна зарплатна схема:

- користувач задає місячну ставку;
- погодинна ставка для нових змін рахується автоматично як `місячна ставка / кількість робочих днів 5/2 у місяці / 8`;
- грейд не збільшує погодинну ставку й заробіток за відпрацьований час;
- окрема грейдова премія за повний місяць = базова місячна ставка зі snapshot місяця × накопичувальний відсоток поточного грейду;
- для повного календарного місяця `Очікується` = заробіток за зміни + фіксована місячна премія + грейдова премія;
- для довільного або неповного діапазону фіксована та грейдова місячні премії не додаються;
- робочі дні 5/2 = понеділок-пʼятниця календарного місяця, без урахування свят;
- у запис зміни копіюються базові `baseHourlyRateSnapshot` і сумісний `hourlyRateSnapshot` з однаковим значенням, а також окремий snapshot грейду;
- старі зміни не перераховуються автоматично після зміни місячної ставки, тільки через явну дію користувача.

## Тікети, простій і виробіток

- У зміні може бути лише один активний тікет.
- Новий тікет не можна почати, доки попередній явно не завершено.
- Для завершення тікета обовʼязкова ціла фактична кількість від `0`.
- Старі тікети без факту позначаються як незаповнені та не входять у числові виробничі підсумки.
- Простій у тікеті ведеться як підсумкова кількість хвилин без станів початку та завершення.
- Користувач може багаторазово додавати цілі додатні або відʼємні коригування; підсумок не може бути відʼємним або перевищувати тривалість тікета.
- Окремий журнал коригувань простою не зберігається.
- Продуктивний час = тривалість тікета мінус простій.
- Ціль для грейду = `ceil(норма за 8 год × % грейду × продуктивні хвилини / 480)`.
- Досягнутий грейд — найвищий із Г1–Г4, ціль якого виконано; нижче Г1 показується окремо, а за нульового продуктивного часу грейд не визначається.

## Режим інкогніто

Режим інкогніто потрібен для приватності на екрані.

Правила:

- Усі фінансові показники замінюються на нейтральну маску `••••`.
- Редагування грошових полів блокується.
- Нефінансові дані, наприклад часи змін або дати, можуть залишатися видимими.
- Режим не повинен видаляти або псувати реальні фінансові дані.

Будь-яка нова фінансова UI-зона має підтримувати інкогніто з першої реалізації.

## Локальні дані

Дані мають зберігатися локально. Заборонено додавати серверну залежність, авторизацію, віддалену базу або приховані мережеві запити без прямої зміни вимог.

Очікувані категорії даних:

- зміни;
- налаштування зарплати і коефіцієнтів;
- стан інкогніто;
- імпортований графік підприємства;
- історія backup/import/export, якщо буде потрібно для UX.

Для складної локальної моделі бажано мати шар репозиторію або сервісів, щоб UI не працював напряму з деталями збереження.

## Backup, import і export

Backup/import/export працює через JSON.

Вимоги:

- Експорт має включати всі дані, потрібні для відновлення роботи додатку.
- JSON backup має мати версію схеми.
- Імпорт має валідувати структуру і не приймати очевидно зламані дані.
- Перед заміною локальних даних імпортом UI має попереджати користувача.
- Фінансові та змінні дані після імпорту мають проходити ті самі доменні правила, що й ручно створені дані.

## Імпорт графіка підприємства

Графік підприємства імпортується текстом.

Підтримувані формати включають блоки `--дд.мм.рррр--` з полями `In time:`, `Out time:`, `Total:` та рядки виду `дд.мм.рррр In time 06:01`. Значення `-` і порожній `Total :` позначають день без запису та пропускаються.

Майбутня логіка має вміти:

- приймати сирий текст графіка;
- розпізнавати дати і зміни, якщо формат це дозволяє;
- показувати користувачу результат перед застосуванням;
- пропускати або позначати неоднозначні рядки;
- порівнювати імпортований графік з фактично відпрацьованими змінами, якщо ця функція реалізована.

## UI/UX принципи

- Основний сценарій має бути зручним однією рукою на мобільному.
- Таймер має чітко показувати поточний стан: немає активної зміни, зміна активна, зміна завершена.
- Грошові показники мають бути помітними, крім режиму інкогніто.
- Дії `Прийшов` і `Пішов` мають мати hold-to-confirm взаємодію.
- Онбординг має збирати тільки те, що потрібно для старту.
- Налаштування мають ясно відділяти фінансові поля від приватності, backup/import/export і графіка.
- Тема має три режими: системна, світла і темна; типовий режим — системний.
- Ручний вибір теми зберігається локально та застосовується на всіх екранах.

## Тестові пріоритети

Першочергово тестувати:

- автоматичне визначення типу зміни;
- обмеження максимум однієї зміни на день;
- заборону більше однієї активної зміни;
- розрахунок грошей;
- поведінку інкогніто;
- JSON export/import;
- завершення тікета з фактом, простій, цілі грейдів і виробничі агрегати;
- окрему базову зарплату, фіксовану та грейдову премії;
- міграції IndexedDB і backup-схеми;
- парсинг текстового графіка підприємства.

UI-тести доречні для hold-to-confirm кнопок, онбордингу, інкогніто і критичних станів таймера.

## План майбутніх сесій

Рекомендований порядок роботи:

1. Зафіксувати доменні типи і сервіси для змін, грошей та налаштувань.
2. Додати або перевірити локальне збереження даних.
3. Реалізувати таймер із hold-to-confirm діями.
4. Реалізувати історію змін.
5. Реалізувати налаштування зарплати та інкогніто.
6. Реалізувати аналітику з фокусом на гроші.
7. Реалізувати графік і текстовий імпорт графіка підприємства.
8. Додати JSON export/import.
9. Додати онбординг.
10. Провести фінальну мобільну і PWA-перевірку.

Цей план можна змінювати, але не можна втрачати offline-first модель і доменні інваріанти.

## Відкриті питання

Питання, які варто уточнити перед реалізацією відповідних частин:

- Як рахувати запізнення і ранній вихід?

- Чи має імпорт JSON повністю замінювати локальні дані або підтримувати merge?
- Яка мінімальна підтримувана версія мобільних браузерів?
